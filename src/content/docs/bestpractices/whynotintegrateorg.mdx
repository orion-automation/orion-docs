## 1. 背景与常见疑问

在 ORION 平台的实施与对接过程中，业务专家和技术团队常会提出一个疑问：

> **“现实中的企业组织架构通常是具有复杂层级（树状或矩阵式）的，但为什么 ORION 平台内的组织与人员信息设计是完全打平的（无层级结构）？这两者在实际业务中应当如何映射？”**

本文档旨在阐明该设计的底层架构哲学，并提供标准的对接与双向映射方案。

## 2. 设计哲学：为什么选择“打平”？

ORION 的核心定位是**下一代企业级业务编排中枢**。我们坚持“关注点分离”的架构原则，将业务流程的流转逻辑与企业的行政管理逻辑彻底解耦。

### 2.1 遵循 BPMN 2.0 标准与核心引擎架构

基于 ORION 的核心引擎架构，BPMN 2.0 规范中的人工任务（User Task）在定义时，并不需要且不应该耦合任何外部的物理组织结构。
引擎在流转到人工节点时，只需要两类核心权限对象：

- **Assignee（处理人）：** 具体的单一用户 ID。
- **Candidate Groups / Candidate Users（候选组/人）：** 扁平的权限集合或角色 ID。

BPMN 模型的职责是定义“谁（哪个角色/ID）在这个环节应该做什么”，而非“这个人在公司属于哪个部门，或汇报线是什么”。

### 2.2 业务编排与身份管理（IAM）的边界隔离

中大型企业通常已具备成熟的组织架构主数据源（如统一身份认证中心、AD、LDAP、HR 系统）。如果 ORION 在内部复刻一套树状组织架构，会导致严重的数据冗余和双向同步一致性问题。打平的设计使 ORION 能够纯粹地利用企业现有的身份主数据，实现单一数据源（Single Source of Truth）。

### 2.3 保持流程模型的高度可移植性与敏捷性

现代企业的组织架构是动态变动的。如果将“华东区-销售部-大区经理”这种层级硬编码进流程定义中，一旦组织变动，流程模型就需要大面积重构。使用扁平化的 ID 和角色标签，可以让流程模型在不修改的情况下，灵活适应外部组织结构的演进。

BPMN 模型不应是“一次性代码”，而应是企业可沉淀、可复用的数字资产。解耦设计赋予了流程模型极强的可移植性，具体体现在：

- **CI/CD 无缝迁移：** 模型中仅包含如 `Role_Financial_Approver` 的抽象标签。同一份 `.bpmn` 文件在开发、测试、UAT 和生产环境中保持绝对一致，无需根据不同环境的人员结构修改模型，完美契合自动化部署要求。
- **跨分支机构复用：** 集团企业只需定义一套标准业务流程（如标准化采购审批）。子公司 A（矩阵管理）和子公司 B（树状管理）共用同一模型。引擎在运行时分别向两地的 IAM 解析相同的角色标签，实现“业务逻辑统一，组织映射隔离”。
- **行业模板开箱即用：** 剥离了组织层级后，ORION 沉淀的行业最佳实践模板可以轻松跨客户流转。新客户导入模型后，只需在后台将自身的统一认证群组与模板中的扁平 ID 进行映射，即可快速上线。

## 3. 落地实践：双向驱动的映射与集成方案

在现实交付中，ORION 并不孤立运行，而是与客户的统一认证系统（SSO/IAM）进行深度集成。现实中的复杂层级映射为扁平对象，是通过**前台 API 驱动**与**后台运行时解析**双向机制共同实现的。

### 3.1 前台交互：基于统一认证（SSO）的 API 驱动

这是用户在 ORION 任务中心（Task Center）最核心的交互链路。系统不需要同步完整的组织架构树，而是通过 Token 携带的扁平 ID 完成闭环：

1. **用户登录与鉴权：** 用户通过企业的统一认证系统登录 ORION 平台。
2. **获取扁平身份凭证：** 登录成功后，统一认证系统会下发包含该用户当前身份信息的 Token。这个 Token 中已经提取并打平了该用户的 `User ID` 以及他所属的各类 `Group ID`（角色、部门标签等）。
3. **API 请求任务：** 任务中心前端直接使用 Token 中解析出的这些扁平化 `User ID` 和 `Group ID`，向 ORION 引擎发起 API 请求，查询该用户有权限处理的 User Task。
4. **解耦优势：** 在这个过程中，ORION 完全不需要知道该用户在企业架构中的具体层级位置，只通过认证中心分发的扁平 ID 即可精准匹配并返回待办任务。

### 3.2 权限抽象与扁平化标签（Tagging）

在流程建模阶段，现实中的树状审批节点会被抽象为扁平的“角色/权限 ID”。

- **物理现实：** 报销流程需要“直属部门经理”审批，金额大于 5 万需要“分管副总裁”审批。
- **ORION 映射：** 流程模型中仅定义节点 A 的候选组为 `Role_Dept_Manager`，节点 B 的候选组为 `Role_VP`。只要用户的 SSO Token 中携带了对应的标签，即可通过 API 拉取到该任务，完美规避了汇报线的强耦合。

### 3.3 后台路由：运行时动态解析与适配层

除了前台通过 Token 主动拉取，ORION 引擎在后台执行路由时同样支持与组织架构的动态对接：

- 当流程引擎流转到某个人工节点，需要动态决定下一环节的扁平 ID（例如：需要动态推断发起人的“直属主管”具体是谁的 User ID）时，引擎可以通过 SPI（服务提供者接口）向客户的真实组织架构服务发起实时查询。
- 通过部署一层轻量级的**身份适配层（Adapter Layer）**，把客户复杂的“树状查询”翻译成 ORION 需要的“扁平 ID”并返回给引擎。

## 4. 总结

ORION 不定义企业组织架构，我们只定义**基于权限对象的执行规则**。
通过打平的组织信息设计以及与企业统一认证体系的双向无缝集成，ORION 既能通过 API 接口让用户极速获取任务，又能通过底层机制灵活适应任何复杂的组织演进。这种解耦设计保障了编排中枢的极致轻量、高性能与强扩展性，是企业级自动化底座的最佳实践。
