在 Diátaxis 框架中，如果说 Tutorial（教程）是“手把手教新手学骑自行车”，那么 **How-to guides（操作指南）则是“给熟练的外卖骑手提供一条避开拥堵的最优送餐路线”**。

结合 ORION 操作系统专注于企业级业务编排（Business Orchestration）与 Agentic Automation 的底层架构特性，我们的 How-to 文档必须聚焦于**真实世界的问题解决**，帮助具备专业胜任力的架构师和开发者在复杂的业务契约和规则流中，顺畅地“把事情做完”。

---

## 一、 核心定位与设计假设

How-to guides 是一份方向指引（Directions），核心目的是目标导向的现实问题解答（Goal-oriented）。

* **假设用户已具备胜任力（Competent User）：** 你的读者明确知道自己想要达到什么业务目的（例如：如何处理高并发下的状态机流转），且具备基础的系统操作能力。
* **拒绝教学（No Teaching）：** 这不是一堂课，而是一份**菜谱（Recipe）**。大厨看菜谱是为了确认调配比例，而不是学习如何切菜。指南中**绝对不需要**教导、解释原理或进行偏题讨论。
* **非端到端闭环：** 它不需要像教程那样从零开始。它可以从某个合理的中间节点开始，到另一个节点结束，要求用户自行将其与实际的业务编排对接。

## 二、 ORION 核心编写原则

### 1. 聚焦真实世界，拥抱复杂性
指南必须从“人类解决业务诉求”的视角出发，而不是“机器界面”的视角。现实中的业务编排（如 IoT 传感器数据处理、企业合同流转）往往不是线性的。优秀的指南必须具备**可适应性（Adaptable）**，允许用户根据真实的业务契约或硬件资源情况进行参数替换与条件判断。

:::tip[正确视角：基于用户的真实业务诉求]
**《如何为高并发的合同审批流配置合理的数据库连接池回收策略》**
聚焦于解决现实世界的性能瓶颈和业务场景。
:::

:::danger[错误视角：基于机器的界面交互逻辑]
**“要部署配置，请选择选项并点击 Deploy 按钮。”**
这属于无意义的系统废话，懂界面交互的用户不需要这种指导。
:::

### 2. 追求顺畅的“工作流 (Flow)”
步骤必须符合架构师在真实工作中的思维节奏。如果要求用户在不同的工具、引擎上下文（如从 Camunda 控制台跳回代码 IDE）之间反复横跳，就会破坏操作的节奏感。最顶级的指南就像一个默契的助手，在用户刚好需要配置参数时，准确的代码段已经递到了手边。

### 3. 精确的标题与动作指令

标题必须精确说明解决什么问题，严格以“如何 (How to)”开头，严防文档类型模糊。

:::tip[绝佳标题]
**《如何集成应用程序性能监控》**
读者能立刻明确这是一篇指导具体实操的 How-to 文档。
:::

:::caution[糟糕标题]
**《集成应用程序性能监控》**
动名词作标题，读者无法预判这是在探讨“是否应该做”，还是在教“如何做”。
:::

:::danger[极差标题]
**《应用程序性能监控》**
完全丢失文档类型，极易与概念解释（Explanation）或参考手册（Reference）混淆。
:::

**无情剥离参考信息：** 绝不要在指南里穷举 API 参数。遇到参数列表，直接使用占位链接将其踢出主干道：“有关完整的参数列表，请参阅 Reference 手册。”

  <TabItem label="步骤 1：生成内容 (Markdown)">
    使用此 Prompt 确保 AI 生成的内容 100% 聚焦于行动指令，无任何冗余的原理教学。
    
    ```markdown
    # Role
    你是一位世界级、极其挑剔的技术文档专家，精通 Diátaxis 现代技术文档架构组织法中的 "How-to guides"（操作指南）核心方法论。同时，你对专注于企业级业务编排（Business Orchestration）与 Agentic Automation、核心编排引擎显式基于 Camunda 7 的下一代操作系统（OS）ORION 有着深度架构认知。

    # Task
    请严格基于 Diátaxis 的 "How-to guides" 哲学，为 ORION 系统的某一具体高级场景或特定任务，编写一份面向具备专业胜任力（Competent User）的系统架构师或开发者的操作指南。

    # Product Rules (ORION Core Context)
    1. 定位：ORION 是企业级操作系统。核心理念是业务运行基于“合同、规则、资源”的显式编排，系统行为具有极强的确定性。
    2. 引擎：核心引擎基于 Camunda 7，遵循 BPMN 2.0 规范。
    3. 语调基调：保持极度谦逊、技术化和务实，无宏大叙事。

    # Documentation Constraints (Diátaxis "How-to" Specification)
    1. 【拒绝教学】假设用户已经知道要达成什么目标，具备基础操作能力。绝对禁止包含基础概念解释、系统原理剖析或冗长前置教学。
    2. 【动作至上】内容必须是 100% 的行动指令（Action and only action）。任何导致操作流中断的背景发散必须被无情抹杀。
    3. 【拥抱真实复杂性】解决方案需具备“可适应性（Adaptable）”，允许架构师根据真实并发量或规则集进行参数替换。
    4. 【标准语言范式】
       - 标题严格采用：“如何（How to）...” 格式。
       - 使用条件祈使句引导动作：“如果你需要实现 X 规则，请配置 Y。”
       - 遇到大量参数时，必须使用占位链接：“关于完整的 API 参数列表，请参阅 [Reference Guide]。”

    # Input Information
    - 核心任务/面临的问题：[输入目标，例如：如何在 ORION 中为 IoT 传感器数据配置基于时间的异常重试与退避策略]
    - 涉及的核心组件：[输入组件，例如：BPMN Timer Event, Camunda Job Executor]
    - 前置假设：[输入前提，例如：用户已成功接入网关并熟悉 BPMN 建模]

    # Output Format
    严格按照以下结构输出，呈现专业、直接的操作流：
    ## 标题：如何 [精确描述任务]
    ### 1. 目标与适用场景 (The Goal) [1-2 句话明确说明解决什么现实问题]
    ### 2. 操作序列 (The Actions)
       #### 步骤 1: [动作导向的小标题]
       - **操作指令**: [清晰的路径、代码或 XML 修改]
       - **决策点**: [条件引导，如“如果延迟较高，建议...”]
       #### 步骤 2: ...
    ### 3. 验证与排错指引 (Validation) [一句话说明如何确认成功]
    ### 4. 相关参考 (See Also) [提供 1-2 个指向 Reference 或 Explanation 的占位链接]
    ```
