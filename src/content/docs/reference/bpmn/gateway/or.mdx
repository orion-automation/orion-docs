## 1. 描述 (Description)

包容网关（Inclusive Gateway，通常简称 OR 网关）可以被视为排他网关与并行网关的结合体。像排他网关一样，它会评估输出顺序流上的条件；同时，它又像并行网关一样，能够接收多条输入顺序流。

在 ORION 平台中，包容网关用于处理“一个或多个（One or more）”的路由场景。基于企业真实的契约与资源分配，当业务规则允许同时触发多个不冲突的业务分支时，它是原生的最优选择。

## 3. 分流与汇聚行为约束 (Diverging & Converging Behaviors)

包容网关的实际物理行为（分流、汇聚或两者兼有）取决于连接到它的顺序流拓扑。如果网关同时拥有多条输入和多条输出连线，引擎会先执行汇聚逻辑，然后再进行分流派发。

### 3.1 分流行为 (Fork)
* **并发评估**：网关会无条件评估所有输出顺序流的条件。对于每一个评估为 `true` 的条件，都会派生出一条并行的执行流（Token）。

### 3.2 汇聚行为 (Join)
* **基于活动的等待**：所有到达的并发执行流都会在此挂起，直到**每一条拥有 Token 的输入顺序流**都有执行流到达。
* **智能按需等待**：与并行网关（盲目等待所有物理连线）的重要区别在于，包容网关**只会等待那些实际被执行的输入连线**。汇聚完成后，流程合并继续向下游推进。
* **非平衡拓扑合法性**：包容网关不需要严格对称或平衡。它单纯只等待所有能到达的输入流，并为满足条件的输出流创建新路径，不受模型中其他结构的直接影响。


## 4. 引擎底层特殊触发行为 (Engine-Specific Behaviors)

在 ORION 引擎底层的汇聚机制中，包容网关的触发时机具有极度特殊的判定公式，这是架构师排查死锁与重复执行问题的关键区域。

### 4.1 核心触发放行条件 (Trigger Conditions)
引擎在判断包容网关是否可以放行时，遵循以下两条核心法则，满足其一即刻触发：
1. **数量达标触发**：网关接收到的 Token 数量**大于或等于**其物理输入顺序流的总数。需要特别注意的是，底层判定**并不强制要求这些 Token 必须从不同的顺序流到达**。
2. **枯竭判定触发**：网关接收到的 Token 数量虽然小于输入连线数量，但引擎通过图遍历计算后判定**已经没有任何其他 Token 能够到达该网关**。

### 4.2 中断与丢失陷阱 (Interruption & Token Loss)
如果在等待汇聚期间，某个原本预期会到达该网关的 Token 发生了路径改变（例如：被边界事件中断并引导至其他路径），导致它永远无法抵达该网关，那么对应的汇聚动作将不会被该 Token 触发。引擎会转而依赖上述的“枯竭判定”来决定是否放行。

### 4.3 同一连线多 Token 到达异常 (Multiple Tokens on Same Flow)
当流程拓扑中由于上游设计（如并行网关被多次重复触发），导致有多个 Token 沿着**同一条输入连线**到达同一个包容网关时：
* 引擎会对第一个到达的 Token 立即触发一次放行，当第二个 Token 随后到达同一连线时，由于满足引擎内部的放行条件，网关会**再次被触发**。
* 这种机制会导致下游的节点被多次实例化（例如本应执行一次的 User Task 会被异常创建两次）。在某些复杂的并发场景中，这种物理行为可能与预期的 BPMN 2.0 理论规范产生冲突。

:::danger[复杂场景下的建议]
在存在并发 Token 可能重叠或逻辑极度复杂的场景下，包容网关的预测行为极难掌控。此时，强烈建议使用结构更确定、逻辑更显式的**排他网关 (Exclusive Gateway)** 来替代包容网关重构判断逻辑。
:::


## 5. 引擎级技术属性 (Engine Execution Properties)

| 属性名称 (UI Label) | 数据类型 | 默认值 | 约束与事实描述 |
| :--- | :--- | :--- | :--- |
| **Async Before** | Boolean | `false` | 强制切断数据库事务。鉴于包容汇聚网关需要进行复杂的图枯竭遍历扫描，强烈建议开启此选项，将计算压力转移至异步队列。 |
| **Async After** | Boolean | `false` | 强制在离开该网关前切断数据库事务。 |
| **Exclusive** | Boolean | `true` | （需配合 Async）确保并发事务不被交叉拾取。 |
