## 1. 描述 (Description)

并行网关（Parallel Gateway，通常简称 AND 网关）用于在流程模型中显式地引入并发性（Concurrency）。

在 ORION 平台的企业级流转中，并行网关是实现跨部门协同（例如：订单生成后，物流部门“发货”与财务部门“收款”同时并行处理）的核心基础设施。与排他网关（XOR）严格的条件求值不同，并行网关**绝对不评估任何数据条件**，它的物理行为完全取决于其连接的拓扑结构。


## 2. 核心属性定义 (Core Property Definitions)

并行网关自身没有复杂的业务属性配置。其最核心的架构规则在于对下游连线条件的“无视”。

| 属性名称 (UI Label) | 对应 XML / 扩展 | 数据类型 | 事实描述与约束 |
| :--- | :--- | :--- | :--- |
| **元素编号 (ID)** | `id` | String | 引擎内的唯一物理标识。 |
| **元素名称 (Name)** | `name` | String | （可选）人类可读的业务名称。 |

:::caution[强制忽略条件机制 (Conditions Ignored)]
并行网关**不计算任何条件**。如果用户强行在连接到并行网关下游的输出顺序流（Outgoing Sequence Flow）上配置了条件表达式，ORION 引擎在运行时会**直接且永远地忽略这些条件**。
:::



## 3. 并发分流与汇聚行为约束 (Forking & Joining Behaviors)

并行网关的实际物理行为（分流、汇聚或两者兼有）完全由它所连接的输入与输出顺序流的数量决定。

### 3.1 分流行为 (Fork)
当网关具备 **1 条输入流** 和 **多条输出流** 时：
* **系统行为**：所有输出的顺序流都将被无条件跟随。引擎会为每一条输出连线克隆出一个全新的并发执行流（Token）。

### 3.2 汇聚行为 (Join)
当网关具备 **多条输入流** 和 **1 条输出流** 时：
* **系统行为**：到达该网关的并发执行流将被挂起并等待。引擎会一直阻塞在这里，直到**每一条输入顺序流**上都到达了一个执行流（Token）。当所有路径都对齐后，网关放行，流程合并为单根执行流继续向下游推进。

### 3.3 复合行为 (Fork & Join)
当网关同时具备 **多条输入流** 和 **多条输出流** 时：
* **执行时序**：引擎会严格按照先后顺序执行。首先执行**汇聚（Join）**逻辑，挂起等待所有输入流到达；汇聚完成后，立即执行**分流（Fork）**逻辑，为所有输出连线生成新的并发执行流。

### 3.4 非对称拓扑约束 (Unbalanced Gateways)
在 BPMN 2.0 规范与 ORION 引擎中，并行网关**不需要“对称/平衡”**。
* **合法性**：模型中不需要强制出现“一个分流网关必须对应一个同等数量的汇聚网关”的结构。一个并行网关会单纯、机械地等待它物理连接的所有输入流，而不受流程模型中其他架构拓扑的影响。


## 4. 底层特殊限制：Token 计数限制 (Token Counting Limitation)

在理解 ORION 引擎底层的汇聚（Join）物理实现时，必须注意一个极易引发严重并发限制的机制。

:::danger[按数量触发机制 (Trigger by Count, Not by Wire)]
在底层的汇聚逻辑中，并行网关的触发条件是：**“已到达的 Token 数量” 等于 “输入顺序流的总数量”**。它**并不强制要求** Token 必须从每一根不同的输入线上分别到达。如果由于上游设计失误（如存在循环或异常重试流），导致同一个输入分支连续向该网关发送了两个 Token，网关的计数器也会加 2。一旦总到达数满足输入线数量，网关就会立刻放行（可能导致部分分支的真正执行流被抛弃或流程状态机错乱）。
:::



## 5. 引擎底层线程执行模型 (Thread Execution Model)

这是架构设计中最容易产生误判的物理边界。BPMN 语义上的“并行”，在引擎底层默认是**单线程串行执行**的。

* **单线程串行 (Default Sequential Execution)**：当执行流到达并行分流网关时，ORION 引擎主线程会选择第一条分支，**同步向下执行**，直到遇到一个事务等待状态（如 User Task 或外部系统回调）。随后，主线程的状态机回退至网关，继续执行第二条分支。它们共享同一个物理线程和数据库事务，而非同时占用多个 CPU 核心。
* **物理多线程并行 (True Parallelism)**：如果并行分支中包含密集的 CPU 计算逻辑（如本地复杂数据转换），为了不阻塞主线程并实现真正的并行计算，**必须在并行网关下游的节点上强制开启 `Async Before` 属性**。这会将任务切分并抛给引擎后端的 Job Executor 线程池，由多个物理线程并发拾取执行。


## 6. 引擎级技术属性 (Engine Execution Properties)

以下属性决定了并发事务在底层数据库与线程池中的执行边界。

| 属性名称 (UI Label) | 数据类型 | 默认值 | 约束与事实描述 |
| :--- | :--- | :--- | :--- |
| **Async Before** | Boolean | `false` | 强制切断数据库事务。由于分流操作会在内存中瞬间生成多个执行流，在极高并发的场景下，建议开启此选项，将事务提交的压力交由 Job Executor 异步削峰。 |
| **Async After** | Boolean | `false` | 强制在离开该网关前切断数据库事务。 |
| **Exclusive** | Boolean | `true` | （需配合 Async）确保同一流程实例的异步并发 Job 不被多线程交叉拾取，防止乐观锁异常（Optimistic Locking Exception）。 |
