## 1. 描述 (Description)

取消（Cancel）与补偿（Compensation）事件是 ORION 平台处理长时业务事务（Long-Running Transactions）与执行业务回滚的核心构件。

在企业级编排中（如：跨系统的联合采购、分布式节点的状态协同），如果某个后置环节失败，底层数据库无法跨域回滚。此时，必须通过抛出**取消事件**来阻断当前事务，并级联触发**补偿事件**，执行与之前成功节点完全相反的业务契约（如：调用退款接口、释放已锁定的库存）。



## 2. 取消事件定义属性 (Cancel Events)

取消事件的物理作用域被严苛限制，**它必须且只能与事务子流程（Transaction Subprocess）结合使用**。

### 2.1 取消结束事件 (Cancel End Event)
* **系统行为**：当执行流到达事务子流程内部的取消结束事件时，引擎会抛出一个取消事件信号。
* **上下文约束**：只能放置在事务子流程内部。

### 2.2 取消边界事件 (Cancel Boundary Event)
用于拦截事务子流程抛出的取消信号，并统筹回滚逻辑。
* **唯一性限制**：一个事务子流程**只允许附加一个**取消边界事件。
* **中断与回滚行为**：触发后，引擎首先会**强行中断**当前事务子流程域内的所有活跃执行流。随后，它会自动启动该事务作用域内所有已激活的补偿事件。
* **同步阻塞契约**：补偿过程是**同步执行**的。取消边界事件会一直挂起等待，直到所有补偿动作彻底完成，执行流才会沿边界连线离开事务节点。
* **多实例级联熔断**：如果取消边界事件附加在一个多实例（Multi-instance）的事务子流程上，只要其中一个实例触发了取消，引擎会直接**取消所有正在运行的并行实例**。
* **中断本质**：由于其语义就是摧毁事务，它永远是中断型的，属性面板不支持配置中断属性。



## 3. 补偿事件定义属性 (Compensation Events)

补偿事件用于绑定、抛出和处理具体的“反向撤销逻辑”。

### 3.1 补偿边界事件 (Compensation Boundary Event)
用于将一个具体的补偿处理器（Compensation Handler，如撤销订单的 Service Task）绑定到某个业务节点上。
* **激活生命周期**：与其他在节点启动时激活的边界事件不同，补偿边界事件**只有在该活动成功完成（Completed Successfully）后才会被激活**。
* **订阅映射**：激活后，引擎为其创建一个隐式的事件订阅。该订阅在补偿被触发，或整个流程实例结束时才会被销毁。
* **多实例与循环累计**：如果依附于多实例或循环节点，节点每成功执行一次，就会累加创建一个补偿订阅。触发补偿时，补偿处理器会被**精确调用相同的次数**。

### 3.2 补偿抛出事件 (Intermediate/End Throwing Compensation Event)
用于主动触发回滚逻辑。补偿抛出事件与补偿结束事件的底层行为完全一致，且当前引擎不支持异步补偿触发。
* **定向补偿 (Targeted)**：通过配置目标活动引用，可以精准触发某个特定节点的补偿逻辑。
* **范围补偿 (Scope)**：如果不指定具体节点，它将触发当前作用域内**所有**已成功完成活动的补偿逻辑，包括并发分支上的节点。
* **层级隔离**：补偿信号会向嵌套的作用域内部递归传递。但**绝对不会向上层传播**。在子流程内部抛出补偿，无法触发子流程外部节点的补偿。且补偿信号**无法穿透传播**给由调用活动（Call Activity）生成的独立子流程实例。

### 3.3 补偿事件子流程 (Compensation Event Subprocess Start Event)
用于为复杂的嵌入式子流程（Embedded Subprocess）定义整体的补偿逻辑。
* **唯一性与互斥**：不能用于顶级流程级。在同一子流程层级中只能存在一个。**严禁**在一个子流程上同时使用补偿边界事件与内部的补偿事件子流程。
* **信号黑洞 (Event Consumption)**：事件子流程会 **吞没（Consume）** 抛入的补偿信号。这意味着子流程内部的其他活动默认不会再被补偿，除非在事件子流程内部显式配置递归触发逻辑。
* **调用契约**：与边界事件相同，只有当主子流程成功完成后，其内部的补偿事件子流程才具备被唤醒的资格。完成多少次，就可被唤醒多少次。



## 4. 核心架构机制 (Core Architectural Mechanics)

在处理补偿流转时，引擎底层遵循两个极具企业级严谨性的物理法则：

### 4.1 逆序执行法则 (Reverse Order of Execution)
当作用域内存在多个补偿处理器需要执行时，引擎将通过并发执行来处理。但在启动这些并发执行流时，引擎严格遵循**反向执行顺序**：业务流中最后成功完成的节点，将最先启动其补偿逻辑。这完美契合了栈式的资源释放原则。

### 4.2 严格的成功完成屏障 (Successful Completion Barrier)
补偿具有严格的时序屏障：**未成功完成的节点，绝不补偿**。
* 如果在子流程执行到一半时发生错误抛出补偿，那么子流程内尚未完成的任务（及其内部挂载的补偿处理器）将**直接被忽略**。
* 对于多实例任务，必须等待**所有实例全部结束**后，该节点才算成功完成，进而具备被补偿的资格。



## 5. 变量快照与作用域 (Variable Snapshots)

在执行补偿处理器时，由于时间线已经回溯，此时流程实例中的全局变量可能已被后续节点污染。为此，ORION 引擎底层设计了**变量快照 (Variable Snapshot)** 机制。

:::caution[局部快照与全局穿透机制]
* **局部快照冻结**：当一个嵌入式子流程成功完成时，引擎会为该子流程作用域内的**局部变量**拍下一张快照。当未来触发补偿时，补偿处理器读取的局部变量，是子流程完成那一刻的冻结状态。**注：引擎仅为嵌入式子流程拍摄快照，不会为普通单一任务拍快照**。
* **增量变量不可见**：快照生成后，子流程作用域内后续新增的并发执行变量，对补偿处理器不可见。
* **全局变量穿透**：快照**不包含**上层作用域（如整个顶级流程实例）的全局变量。当补偿处理器尝试读取全局变量时，它获取的是**当前触发补偿这一刻的最实时状态**。
:::
