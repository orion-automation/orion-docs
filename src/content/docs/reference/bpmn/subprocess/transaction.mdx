## 1. 描述 (Description)

事务子流程（Transaction Subprocess）是一种特殊的嵌入式子流程，用于将多个活动作为一个逻辑工作单元进行分组。

在 ORION 平台中，事务子流程是处理分布式复杂操作（如跨系统的资源预订与扣款）的原生编排容器。它确保内部的分组活动在业务层面上要么全部成功，要么集体失败。


## 2. 事务的三种终态逻辑 (Three Possible Outcomes)

当执行流进入事务子流程后，其最终生命周期必定归宿于以下三种状态之一：

### 2.1 成功 (Successful)
* **判定条件**：如果事务既未被内部的取消事件主动撤销，也未因未捕获的严重异常（Hazard）而终止，则视为成功完成。
* **流转行为**：执行流将沿着事务子流程的输出顺序流正常离开。
* **补偿契约**：与普通的嵌入式子流程一样，成功完成的事务子流程可以在流程的后续阶段，通过抛出中间补偿事件被整体回滚。

### 2.2 取消 (Canceled)
* **判定条件**：当执行流在事务作用域内部到达**取消结束事件 (Cancel End Event)** 时，事务被判定为取消。
* **流转行为**：引擎将强行终止并移除该作用域内的所有活跃执行流。随后，引擎将唤醒附加在该子流程上的**取消边界事件 (Cancel Boundary Event)**，自动触发补偿机制。
* **离开路径**：当所有补偿动作彻底完成后，执行流将沿着取消边界事件的输出连线离开事务节点。

### 2.3 异常终止 (Hazard)
* **判定条件**：如果抛出了错误事件 (Error Event)，且该错误未在事务的作用域内被捕获（这也适用于错误被事务外边界上的事件捕获的情况），事务将因严重危险而强行终止。
* **核心约束**：在此种灾难性终止的情况下，**系统绝对不会执行任何补偿逻辑**。

## 3. 架构边界：BPMN 事务 vs. ACID 事务 (Relation to ACID Transactions)

在架构设计时，绝对不能将 BPMN 事务子流程与底层的技术级 ACID 事务混为一谈。它们在物理层面上存在本质的差异：

* **生命周期极差**：数据库的 ACID 事务通常寿命极短，而 BPMN 业务事务可能需要耗费数小时、数天甚至数月（例如需要等待用户处理任务，或等待外部业务系统回调）。
* **跨事务物理切分**：由于不可能将底层的技术事务锁保持数天之久，一个 BPMN 事务在物理上必然跨越并被切分为多个底层的 ACID 事务。
* **隔离性丢失 (Loss of Isolation)**：跨越多个底层事务意味着 BPMN 事务失去了传统数据库的隔离性。事务内部的中间状态（例如：酒店已预订，但尚未扣款）是对外部系统完全可见的。
* **无物理回滚 (No Traditional Rollback)**：BPMN 事务无法进行传统意义上的物理回滚。当 BPMN 事务被取消时，早期的部分 ACID 事务早已被提交且无法撤销。

## 4. 领域特定解决方案：补偿与隔离应对 (Domain Specific Solutions)

面对长时业务事务固有的隔离性缺失与无法物理回滚的难题，必须采用业务领域（Domain Specific）的方案来应对：

* **业务补偿替代回滚**：业务的回滚必须依赖补偿（Compensation）机制。如果在事务作用域内抛出了取消事件，所有已经成功执行且配置了补偿处理器的活动，都将被依次补偿撤销。
* **隔离性降级策略**：针对中间状态可见的问题，业务层可以采用诸如“允许一定比例的超售（Overbooking）”或“设定保留超时时间（超时未收到付款则自动取消）”等架构策略来化解。


## 5. 引擎底层限制：乐观并发陷阱 (Optimistic Concurrency Trap)

ORION 引擎以事务化的方式执行流程状态机，底层的并发控制严格依赖于**乐观锁 (Optimistic Locking)**。BPMN 事务的错误、取消和补偿机制全部构建在这一底层机制之上。

:::danger[最佳实践]
在设计高并发的并行事务时，必须警惕以下物理陷阱：
1. **到达即触发原则**：取消结束事件只有在被真正物理到达时才能触发补偿。如果在到达前，某个服务任务抛出了未声明的 Java 系统异常（Undeclared Exception），取消动作将彻底失效。
2. **底层 ACID 否决**：如果由于数据冲突，导致底层 ACID 事务的其他参与者将事务状态标记为 `rollback-only`，那么补偿处理器的执行效果将无法被提交到数据库中。
3. **并发双重触发崩溃**：如果事务内部存在两条并发的执行流，且它们**同时**到达了取消结束事件，引擎会尝试触发两次补偿。这极易导致底层数据版本冲突，并抛出致命的乐观锁异常导致整个业务链路崩溃。
:::
